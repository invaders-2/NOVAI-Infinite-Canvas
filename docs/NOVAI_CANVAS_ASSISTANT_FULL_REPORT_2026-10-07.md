# NOVAI 画布助手完整调研与升级报告

> 版本：2026-10-07｜对象：`NOVAI-v16` 智能画布助手｜目的：解决“助手理解不准，参考图或上下文没用对”，并形成可持续迭代的产品与后端路线。
>
> 证据分级：**已核验**＝当前本地源码或 TapNow 公开文档；**合理推断**＝根据公开行为作出的工程判断；**待实测**＝需要登录后的真实产品或真实模型调用才能证实。本文不把推断写成事实。

## 1. 结论

NOVAI 已有“画布 + 多模型 + 工具执行 + SSE 过程展示”的骨架，问题不在于缺少聊天框，而在于缺少一条可靠的“用户指定素材 → 模型真正看见该素材 → 执行时仍只使用该素材 → 用户能核对结果”的链路。

当前最该优先做的是把参考素材从一串 URL 升级为有身份的输入：每张图带节点 ID、名称、来源、顺序和用途；后端把它转为模型可读的图片内容；提示词明确区分“当前参考”和“仅供理解的选中节点”；失败时直接说明哪一张参考没有送达，绝不静默丢弃或换模型重试。这样才能从根上改善“商品图被当成风格图、换图后仍引用旧图、移除参考后又被带回、长画布前面节点抢走注意力”等体验。

TapNow 的公开资料显示，它把 Agent 做成画布工作流的协调层：用户显式提供节点、附件和 `@` 引用，Agent 先读上下文、列计划、在批准边界内调用对应 App，产物回到画布并可继续引用。它值得借鉴的是上下文选择、输入能力校验、确认卡和可追溯产物，不是照搬其没有公开的内部实现。

## 2. 范围、方法与限制

本报告结合三类资料：TapNow 官网和帮助中心的公开说明；`NOVAI-v16` 当前源码和项目内已有设计文档；对常见多模态 Agent 架构的工程推断。审阅范围包含 `main.py`、`static/js/smart-canvas.js`、项目内 `docs/v2/` 和桌面打包设计。

## 4. TapNow 后端的合理推断

以下是为了指导 NOVAI 设计而做的推断，不能视为对 TapNow 的逆向结论。

1. **画布对象服务**：需要保存节点、连线、媒体元数据、视口、版本及共享/克隆关系；否则无法支持跨会话引用和只读分享。
2. **素材处理层**：上传后应有对象存储、缩略图/预览、媒体类型和尺寸检测；视频还需要抽帧或由支持视频输入的模型处理。
3. **Agent 编排层**：接收用户指令与显式引用，构造上下文，选择可用 App/模型，先计划后执行，保留每步输入、输出与状态。
4. **异步任务层**：图片和视频生成不应依赖一个长 HTTP 请求；需要任务 ID、排队/运行/成功/失败/取消状态、重试边界和结果回写保护。
5. **能力注册表**：模型的输入类型、最大参考数、尺寸、价格和可编辑动作必须机器可读，确认卡才能正确工作。
6. **审计与计费层**：文档提到 Tapies 估算/消耗，合理推断每次模型调用都需要可追踪的输入参数与使用记录。

对 NOVAI 而言，最值得落地的是上述接口边界，而不是猜测内部产品细节。

## 5. NOVAI 当前架构与助手基线（已核验）

### 5.1 应用结构

* 前端是原生 HTML/JavaScript；`index.html` 通过 iframe 切换页面，画布间通信依赖 `postMessage`。智能画布与传统画布是两套独立实现，本文重点为 `static/js/smart-canvas.js`。
* 后端以 `main.py` 为主，承担 FastAPI 路由、模型配置、画布数据、素材、生成分发、任务和对话能力。项目内也有 `server/` 模块，但不能假定所有路由都已经完成拆分。
* 数据主要是 JSON 文件和本地媒体目录。画布节点保存在画布 JSON 中；图片通常作为 `images[]` URL 保存，天然缺少“这张图在本次对话中扮演什么角色”的一等元数据。
* 图片、视频、对话支持多个 Provider；不同 Provider 的多模态能力和请求格式并不相同。模型可用性由本地配置决定，无法只靠前端保证。

项目内既有审计对单体、Provider 分发和任务历史有更完整的历史说明，参见 [架构审计](v2/NOVAI_ARCHITECTURE_AUDIT.md) 和 [V2 变更地图](v2/NOVAI_V2_CHANGE_MAP.md)。这两份文件有历史日期，阅读时应以现行源码为准。

### 5.2 当前 Agent 主路径

`POST /api/agent/run` 以 SSE 返回 `run_start`、`plan`、`step_start`、`step_result`、`message`、`done` 等事件。前端用 `fetch + ReadableStream` 解析 SSE，显示计划卡和执行步骤。Agent 可使用创建节点、更新节点、连线、启动生成、查询任务等工具，并将画布快照和执行结果回灌下一轮模型。

这是一条正确的产品骨架：用户可以看见计划、控制执行，并在画布得到结果。接口契约、历史兼容要求和旧版验证记录见 [Agent 升级接口契约](v2/AGENT_UPGRADE_SPEC.md)。该文件描述的“后端已实现”是当时版本的记录，不能替代本轮针对参考图可靠性的验收。

### 5.3 现有基线中与本问题直接相关的实现

* 前端 `buildAgentFocus()` 当前构造 `selected_node_ids`、`reference_images`、`reference_videos` 和视口；参考在旧契约里是 URL 字符串。
* 后端 `AgentRunFocus` 与 `_agent_run_normalize_focus()` 同样以字符串列表接收图片/视频引用；`_agent_run_focus_text()` 主要把它们写进文字提示。
* `/api/agent/run` 的模型消息当前为 system 文本加 user 文本。项目已有 `/api/canvas-llm` 的多模态消息拼装能力，说明基础转换设施存在，但两条路径需要明确统一，不能默认已经共享。
* 画布摘要和 focus 文本本身有长度限制。若优先级没有以“当前引用、当前选择、上游关联”为中心，大画布容易被早期节点或无关节点占用上下文。

## 6. 用户痛点的根因

用户反馈是“理解不准，参考图或上下文没用对”。这不是单一模型质量问题，至少有六个可修复的工程根因。

| 根因 | 典型表现 | 后果 |
| --- | --- | --- |
| 图片只以 URL 文本进入 Agent | 模型看到的是链接字符，不是视觉内容 | 助手只能猜图，商品/风格/构图必然混淆 |
| 引用没有身份和用途 | 只有 URL，丢失节点名、来源、顺序、角色 | “用商品图做主体、用风格图调色”无法精确表达 |
| 选中与参考混为一谈 | 选中节点既是注意力又可能自动成为媒体输入 | 用户移除参考后仍被偷偷带回，或无关图片干扰生成 |
| 引用快照过期 | 节点图片/标题更新后，对话区仍持有旧数据 | 换图、改名后，助手继续引用旧素材 |
| 大画布摘要无优先级 | 固定截断或按存储顺序取节点 | 当前选中节点和关联节点被挤出上下文 |
| 输入失败被静默处理或错误回退 | 格式、下载、抽帧失败却继续调用模型 | 用户以为助手看过参考，实际没有；还可能重复扣费 |

## 7. 改善方案：把“看见什么”做成可验证的契约

### 7.1 前端引用模型

发送给后端的 focus 建议改为以下形态。`selected_node_ids` 只表示“优先理解哪些节点”；真正会送给模型的视觉输入只来自 `references`。用户移除某张图后，它必须从 `references` 中消失，即便源节点仍被选中。

```json
{
  "selected_node_ids": ["node_product", "node_style"],
  "references": [
    {
      "id": "node_product",
      "name": "商品白底主图",
      "type": "smart-image",
      "source": "node",
      "role": "subject",
      "media": [{"url": "/output/product.png", "kind": "image"}]
    },
    {
      "id": "upload_8",
      "name": "蓝色柔光风格",
      "type": "upload",
      "source": "upload",
      "role": "style",
      "media": [{"url": "/assets/style.jpg", "kind": "image"}]
    }
  ],
  "viewport": {"x": 0, "y": 0, "scale": 1}
}
```

前端行为要求：发送前从当前节点数据刷新标题和媒体；节点已删除时移除对应引用；上传引用单独保存；用户手动移除后记录“本轮排除”，避免同步逻辑重新加回；重新选择该节点可以再显式加入。引用区应展示名称、缩略图和来源，不能只显示难以辨认的 URL。

### 7.2 后端多模态与上下文策略

1. **视觉输入真的进消息**：将引用图转成 Provider 接受的 `image_url` 内容块（本地文件转可访问 URL 或受限 data URL），而不是把 URL 写在文本中。
2. **视频受控处理**：仅在模型不支持直接视频时抽取有限帧；明确说明只理解抽取帧，不声称理解完整视频。抽帧失败即报错，不把视频 URL 当作“已看见”。
3. **严格失败**：本地文件缺失、转换失败、超过模型允许的图/视频数、Provider 不支持视觉输入时返回结构化 `reference_input_error`，停止该轮。不能悄悄删图后继续生成。
4. **同一轮缓存**：一项媒体只转换一次，多轮 Agent 决策复用，降低等待和重复读取。
5. **上下文排序**：顺序应为：活动引用 → 选中节点 → 与它们一跳相连的上游/下游节点 → 其他节点。文本内容为重点节点保留更多长度，背景节点只保留标题、类型和极短摘要。
6. **提示词约束**：系统提示应列出每个活动参考的名称/角色/序号，要求模型在计划和调用中说明使用关系；同时明确“选中节点只是上下文，除非在活动引用里，否则不能作为视觉输入”。
7. **Provider 严格性**：本次带视觉引用时，不因一个 Provider 不可用而静默换成另一个能力未知的模型；清楚告诉用户当前配置不支持，再由用户选择。

### 7.3 任务与结果回写可靠性

生成任务需要在入队前把 `task_id` 写入节点。任务结束回写画布时必须在画布锁内再次核对该节点仍存在、节点记录的任务 ID 仍等于当前任务 ID；旧任务不能覆盖新任务结果，已删除节点也不能被重新写回。模型生成成功与“画布写回成功”要分开记录：后者失败时保存结果和错误信息，不能触发一次新的付费生成来“补救”。

## 8. 当前已核验基线与建议改进的验证边界

截至本报告生成时，已确认仓库存在并可审阅的能力包括：SSE Agent 计划/执行状态展示、用户批准后执行的路径、历史消息长度控制、基础引用 URL 传递、任务状态查询，以及对旧接口的兼容设计。对应代码在 `main.py` 的 `/api/agent/run` 区段和 `static/js/smart-canvas.js` 的 `runAgentStream()` / `buildAgentFocus()` 附近。

“结构化 reference、图片内容块、引用实时刷新、已移除引用不回流、上下文优先排序、任务回写防旧任务覆盖”是本报告提出的实现方案。它们尚未在当前 `NOVAI-v16` 源码中作为本次交付完成或验证，只有落到最终源码并通过下面的测试后，才可以标为“已完成”。

真实验证必须分三层：

1. **单元/接口验证**：构造本地图片、当前引用、移除引用、61 个以上节点、无效文件、任务先后完成等场景，检查发送 payload、上游多模态消息、SSE 错误码和最终画布 JSON。
2. **浏览器验证**：在隔离端口打开真实 `smart-canvas.html`，选择两张图、移除一张、改名/换图、发送指令，确认 UI 显示的引用与请求中 `references` 完全一致；模拟 SSE 断流和失败状态，确认不显示“已完成”。
3. **真实模型抽样**：在已授权且支持视觉输入的同一 Provider 下，以“商品主体 + 风格参考”固定案例验证。人工检查结果是否保留商品、采用风格、未使用已移除素材。模型输出具有随机性，不能用一次成功宣称永久正确。

不能把 `py_compile`、单纯 curl 200、前端字符串搜索或模型文本回复当作“模型看见参考图”的证据。唯一可核验的证据是：上游请求包含正确媒体内容块，且端到端样例的结果、任务记录与画布回写一致。

## 9. P0 / P1 / P2 路线图

### P0：先让引用可信（当前最高优先级）

* 完成结构化 `references` 契约，保留旧 `reference_images/reference_videos` 的兼容读取。
* 让活动参考真实进入多模态消息，失败显式报错，不静默回退。
* 区分“选中用于理解”与“引用用于视觉输入”；修复换图、改名、移除参考后的实时刷新。
* 画布摘要按活动引用和相关节点排序；给重点节点足够文本预算。
* 修复任务状态、SSE `done`、断流和旧任务回写的真实状态表达，避免重复生成。

完成标准：用户选择商品图和风格图、移除其中一张、修改另一张后，最终发送的请求和界面显示都能准确反映当前选择；任一参考无法送达时，生成不启动且错误指出具体素材。

### P1：让创作过程可控

* 引用角色可选：主体、风格、构图、首帧、尾帧、仅供文字理解；自动识别仅做建议，不可代替用户决定。
* 提供生成前确认卡：模型、尺寸、数量、费用估算、将使用的引用缩略图和角色。
* 每个产物保存“来自哪次 run、哪条指令、哪些引用、哪个模型/参数”的谱系；支持从产物回到输入。
* 任务持久化、取消、超时、并发限制和恢复策略；页面刷新后仍可看到任务。
* 对话支持“锁定当前引用集”，避免多轮交流中上下文漂移。

### P2：让助手成为创作搭档

* 面向电商的工作流模板：商品理解 → 卖点/场景 → 主图 → 详情页 → 视频分镜，且每一步引用和审批可见。
* 可解释的素材检索和相似图建议；只在用户同意后加入引用。
* 团队批注、版本对比、角色权限、共享画布的只读解释。
* Provider 能力注册中心与成本预算：按模型约束过滤不可用选项，统一估算成本与输入上限。
* 以真实创作任务建立评测集，持续统计“引用正确率、任务完成率、重复生成率、用户撤销率”。

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| A1 | 选中商品图和风格图 | 请求含两个有 ID/名称/媒体的活动引用，模型消息含两项图像内容 |
| A2 | 移除风格图后发送 | 请求和模型消息只剩商品图；选中节点不会把风格图加回来 |
| A3 | 节点改名、换图后发送 | 引用名称和 URL 是最新值，不使用旧缓存 |
| A4 | 上传图片作为参考 | 上传素材有独立身份，刷新/同步不会丢失 |
| A5 | 61 个以上节点 | 活动引用、选中节点及其关联节点进入摘要；不被前 60 个无关节点挤掉 |
| A6 | 本地图片缺失/格式不支持 | 返回带素材标识的 `reference_input_error`，不发起生成 |
| A7 | 视频无法抽帧 | 明示无法读取该视频参考，不声称已理解视频 |
| A8 | Provider 不支持视觉输入 | 请求在生成前失败，提示选择支持视觉的模型；不静默换 Provider |
| A9 | 任务 A 后启动任务 B | A 晚完成时不能覆盖 B 的节点结果 |
| A10 | 节点已删后任务完成 | 不复活已删除节点；任务记录保留结果与回写状态 |
| A11 | SSE 提前断开 | 界面显示连接中断/未完成，不标成成功；可刷新权威画布状态 |
| A12 | 计划模式 | 未点击执行前不创建付费生成任务；确认卡显示将使用的引用 |
| A13 | 真实模型固定样例 | 人工确认主体图、风格图和已移除图的使用符合指令，并保存 run 记录 |

## 11. 交付、运行与桌面包同步

本报告所在源码工程是 `NOVAI-v16`。开发时可使用项目说明中的启动方式，并在隔离端口验证，避免干扰用户正在使用的桌面服务。源文件变更不会自动进入已经安装的桌面应用；需要按当前桌面打包流程把通过验收的 `main.py`、静态前端和依赖一起构建，再在桌面包中做一次同样的 A1、A2、A6、A9、A11 冒烟验证。

桌面打包的已知设计、目录和验收要求见 [桌面打包设计](superpowers/specs/2026-07-16-desktop-packaging-design.md)。发布前应记录：源码提交版本/构建版本、使用的 Provider、固定测试素材、运行时间、每个验收项结论和失败日志。这样用户实际运行的桌面包与开发目录的行为才可追溯，避免“源码修好了，安装包仍是旧助手”。

## 12. 建议的下一次产品验收话术

用一个具体任务验收，而不要只问“它聪不聪明”：

> 选中“商品白底主图”和“蓝色柔光风格”，把它们分别标成“主体”和“风格”。让助手生成 4:5 的护肤品主图；随后移除风格图并再生成一版。检查确认卡、运行记录和两个结果，确保第二版没有继续使用被移除的蓝色柔光参考。

这个案例同时覆盖引用身份、视觉传输、移除同步、计划确认、生成任务和结果追溯，是当前最能暴露核心问题的验收样例。
