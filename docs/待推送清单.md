## ⏳ 2026-10-24 · APIMart 视频输入图片上传 413（批量生成整行失败）

**状态**：代码已改完并真机/真上游验证，**尚未提交**。客户端已重打包（1.0.136），需要在装过一次之后再双击一次 `更新NOVAI应用.command` 覆盖安装才生效。

**必须一起提交的文件（2 个）**

| 文件 | 状态 | 说明 |
|---|---|---|
| `main.py` | M | APIMart 图片上传改为「按档压缩 + 只有 413 才降档重试」；修正误导性的“不超过 10MB”文案 |
| `tests/test_apimart_upload_shrink.py` | ?? 新增 | 6 个纯函数用例：档位体积递减/尺寸格式、alpha 铺白底、413 降级、全 413 文案、401 不降级 |

**根因**：APIMart（apib.ai）网关 nginx 的请求体上限是 **1 MiB**（实测 1,035,348 字节 200、1,049,620 字节 413），而后端代码按 9.5MB/10MB 假设把本地图原样上传 —— 用户那张 7.4MB 的 PNG 直发必然 413，整行批量生成因此失败。

**改法**：`APIMART_UPLOAD_TIERS = ((900_000,2048),(576_000,1536),(384_000,1280),(256_000,1024))`，唯一压缩入口 `apimart_upload_payload_variants()`，上传时 `apimart_upload_with_shrink()` 逐档重试（只有 413 降档，401/500 立即返回）。

**验收（提交前重跑）**

```bash
cd NOVAI-v16
venv/bin/python -m py_compile main.py
venv/bin/python -m pytest tests/test_apimart_upload_shrink.py -q     # 6 passed
node tests/run-all.js                                               # 93/93
```

真实上游验证（2026-10-24，用用户那张 7.4MB 图走修复后完整路径）：首档产出 377,569 字节 JPEG → POST `/v1/uploads/images` 200 → 返回可访问的 `https://getapib.org/image/...jpg`（GET 该 URL 200）。强制 413 场景：7,747,124→413、1,490,773→413、377,569→200，逐档降级有效。

**`update-notes.json` 建议文案**

- 修复视频批量生成因输入图片过大失败（APIMart 网关 1MB 限制）：本地图片自动压缩并逐档重试

**遗留**

- 视频素材（非图片）上传链未改，若网关同样 1MB 限制仍可能失败。
- 只对 413 降档；若网关改成直接断连则不降档（首档已 ≤900KB，实际不会触发）。
- 其它 APIMart 兼容站上限若更低，最多降到 256KB/1024px，再失败只报明细不无限降。

- 视频编辑任务在输入视频短于 4 秒时直接提示「请输入 4~30 秒的视频」，不再抛出上游的参数错误

**遗留 / 已知边界**

- 远程 http(s) 视频或本机没有 ffprobe 时探不到时长（返回 None），按设计放行，这类短素材仍会到上游报原错——只能拦住本地可探测的视频。
- 只覆盖火山直连 Seedance 分支（本次报错路径）；APIMart、玉玉等其它分支未加。
- 「动作参考视频 + prompt 里带编辑/替换字样」会被判成编辑目标而拦下，与它本来就会被当目标视频提交的行为一致，不算新增误伤。
- 上限 30 秒未校验：现有 >15.2 秒截断逻辑原样保留（那是参考视频 r2v 的限制），编辑任务的上限交给上游。
